# M12 selection interactions

Reviewed 11 October 2026 against primary guidance. This includes recommendations and a bounded source-browser audit, not an accessibility certification or physical-device test. Preserve ClaimClock’s visual design; change the selection interaction where it helps.

## Implemented M12 decision

The implementation uses one real native `<dialog>` picker at every viewport size for the insurer, optional TPA, case and restore-target lists: a centered panel on wider screens and a sheet on narrow screens. Search filters local options; ordinary buttons commit a choice, with one result in the Tab sequence and Arrow/Home/End navigation. This is a dialog with DOM focus inside it, not an ARIA combobox/listbox. The native select remains the underlying value and fallback. Opening on coarse-pointer devices initially focuses the heading so browsing does not automatically summon a keyboard. Three-choice request/outcome controls and other short selects stay native in this scope; the radio recommendation below remains a possible later refinement. No framework, remote search or new dependency was added.

Independent Playwright audit against `http://127.0.0.1:4321` checked 320×460 and 667×300 layouts, Tab/Shift+Tab containment, Arrow/Home/End navigation, Escape/focus return, Hindi alias `केयर`, and cancellation without changing the active case. It reproduced a hidden current selection on first open, scroll leakage between insurer and TPA pickers, and blocked application initialization when the picker module failed. The corrected source passed targeted reruns: restored Zuno and the empty TPA choice were visible; aborting the picker module left native controls usable and actually started a clock and produced a deduction review. Evidence/scripts are in ignored `.cache/agent-picker-audit/`. These Chromium tests emulate touch/viewport conditions; they do not establish real on-screen-keyboard or VoiceOver/TalkBack behavior.

## Recommended controls

| Task | Recommendation | ClaimClock-specific behavior |
|---|---|---|
| Insurer, 32 entries | Progressively enhance the native select with a searchable, single-selection combobox. | Browse the full list without typing; filter locally by official name and existing aliases. Keep the selected insurer visible. Commit its stable ID only on explicit selection. |
| Optional TPA, 17 entries | Reuse the same long-list component if it improves testing results; retaining native select is also reasonable at this size. | Preserve the meaningful empty value, “Not sure / handled by insurer,” as an explicit selectable option. Do not require the visitor to invent a TPA. |
| Case switcher / restore target, up to 50 | A searchable native-dialog picker suits the longer, potentially similar case descriptions. | Show insurer, hospital and date on wrapping rows; clearly mark the current case. Selecting a restore target must not perform replacement—the existing deliberate Replace action remains separate. |
| Request type / outcome, 3 choices | Native radio inputs in a labelled fieldset, styled to fit the existing cards. | All choices remain visible. Do not convert them into tabs or toggle buttons. Preserve existing defaults unless changing the product’s default-answer policy deliberately. |
| Compact settings, e.g. comparison sort | Keep a well-sized native select unless an observed problem justifies enhancement. | Preserve the normal browser keyboard/touch behavior. Do not make every select searchable. |

GOV.UK cautions that some people find selects difficult and recommends considering fewer visible choices. Its radio guidance uses a fieldset/legend and cautions against defaulting answers to questions. This supports the short-list recommendation, not a universal claim that custom controls outperform native controls. [GOV.UK select](https://design-system.service.gov.uk/components/select/), [GOV.UK radios](https://design-system.service.gov.uk/components/radios/).

## Two coherent patterns, not a hybrid

**Combobox:** the labelled input has `role="combobox"`, `aria-expanded`, `aria-controls` and `aria-autocomplete="list"`; its popup is a listbox containing options. DOM focus stays in the input, with `aria-activedescendant` referencing the active, existing option. Maintain a visible focus indicator and keep that option scrolled into view. Down/Up navigate; Enter confirms; Escape dismisses without changing the committed value; Tab leaves the control. Do not turn every option into a Tab stop. Preserve native text-editing shortcuts, selection, Home/End behavior in the input and Hindi IME composition. Choose manual selection: filtering or arrow navigation alone must not switch the active case or silently change the stored insurer. [W3C APG combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/).

**Dialog picker:** use an actual `<dialog>` opened by a labelled button and `showModal()`, not a listbox merely styled as a sheet. Give it a visible title, search field and visible Cancel/Close. Move focus inside; keep Tab/Shift+Tab inside; Escape cancels; restore focus to the opener. Prefer ordinary controls inside: for example, filtered native radio rows followed by “Use selected case.” In that version arrows change a candidate, while Use commits; arrowing through radios must not close the dialog. Do not put Delete, Restore or other buttons inside listbox options. A mobile dialog adaptation must actually move DOM focus into the dialog instead of retaining the combobox’s listbox focus model. [W3C modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [web.dev dialog](https://web.dev/learn/html/dialog).

Implement one shared local filtering/value model in TypeScript, with no framework, network search or heavy dependency. These small lists do not need virtualization. If maintaining two presentation modes proves fragile, use the same tested dialog picker at all sizes, or retain native selection; consistency is preferable to an incomplete custom interaction.

## Native fallback and state

- Render the original labelled select and its options first. Enhance only after initialization succeeds; a missing script must leave selection available. GOV.UK’s accessible-autocomplete demonstrates this strategy, but adopting its package is not required. [Progressive enhancement](https://alphagov.github.io/accessible-autocomplete/#progressive-enhancement).
- Keep one authoritative ID/value and synchronize the native control on commit. Preserve its name, required/disabled state, form reset and validation behavior. Once enhanced, expose only one interactive control to assistive technology. A hidden required select must not cause an unfocusable validation error; route the error to the visible field and test submission.
- Search text is not a valid insurer/case ID. Show a localized no-results state and a clear way back to all choices. Cancel restores the committed selection. Re-rendering after language change, restore, deletion or storage updates must not leave stale options, duplicate IDs or dangling active-descendant references. Keep search and labels local; no new telemetry is needed.

## Mobile and acceptance checks

Use wrapping labels and approximately 44–48 CSS-pixel-high rows/buttons as this product’s touch target. WCAG 2.2’s AA target-size criterion is 24 by 24 CSS pixels with exceptions; the larger product target must not be presented as that criterion’s exact requirement. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Keep input text at least 16px, allow zoom, and retain obvious native-control affordances. [web.dev form styling](https://web.dev/learn/forms/styling-form-controls/). Bound panels to the available viewport with a scrolling results area, visible close action and safe-area spacing. `dvh` helps with expanding browser chrome; **it does not by itself account for the on-screen keyboard**. Test keyboard-open geometry; use measured visual-viewport bounds if needed rather than assuming `100dvh` solves it. [web.dev viewport units](https://web.dev/blog/viewport-units).

Before release, check keyboard-only open/filter/select/cancel/Tab/Shift+Tab; no-results and empty TPA; all 32/17/50 entries; English/Hindi and IME; long labels, zoom and narrow landscape; script failure/native fallback; and modal focus return. On real iOS Safari and Android Chrome, verify that keyboard, browser bars and scrolling never hide the input, active row or dismissal control, and that scrolling cannot accidentally select an item. Include VoiceOver/TalkBack and a desktop screen-reader pass; automation alone does not establish those results. APG explicitly warns of mobile/touch assistive-technology gaps in its examples. [APG implementation warning](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/).
